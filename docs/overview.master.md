**1. High-Level Architecture Overview**
- **App/bootstrap:** GTK app startup and X11 initialization live in `main.cc` (`App::on_activate`), which opens the display, sets up preferences/action watchers, and creates `XState`, `Grabber`, and `Win`. `XTestGrabControl(dpy, True)` is set here, affecting how synthetic events are handled. `main.cc` also defines the global `experimental` flag and `current_app_window`. 
- **Input capture & device management:** `Grabber` (`grabber.cc`, `grabber.h`) owns XI2 device discovery (`Grabber::init_xi`, `Grabber::new_device`), XI2 event masks (`device_mask`, `raw_mask`), and XI2 grabs (`Grabber::grab_xi`, `Grabber::grab_xi_devs`, `XiDevice::grab_button`, `XiDevice::grab_device`). It also tracks window hierarchy and WM state via `Children` and `get_app_window`.
- **Event dispatch & state machine:** `XState` (`handler.cc`, `handler.h`) is the single-threaded dispatcher, pulling X events in `XState::handle`, routing XI2 events to `handle_xi2_event`, and delegating to a handler stack rooted at `Handler` subclasses (Idle/Stroke/Advanced/etc.).
- **Gesture recognition:** `StrokeHandler` (`handler.cc`) collects `PreStroke` points (from XI2 motion), calls `Trace` drawing (`trace.h`, `shape.cc`, etc.), and constructs `Stroke` objects (`gesture.cc`, `stroke.c`) for comparison (`Stroke::compare`).
- **Action mapping & execution:** `ActionDB` (`actiondb.cc/.h`) matches strokes to actions; `Actions` UI (`actions.cc`) creates/records strokes (via `stroke_action`/`recording`). Actions often execute via `XTestFake*` in handlers (e.g., `ButtonHandler`, `ScrollHandler`) or run external commands (`actions.cc`/`actiondb.cc`).
- **GTK/X11/XI2 responsibility split:** GTK UI, dialogs, and menus are in `win.cc`, `prefs.cc`, `actions.cc`. X11/XI2 and input interception are in `grabber.cc` and `handler.cc`.

**2. Detailed Event Flow Walkthrough**
- **Startup wiring:** `App::on_activate` opens the X display, creates `XState` and `Grabber`, attaches a `Glib::IOSource` on the X connection fd to call `XState::handle` (`main.cc`). 
- **Event ingestion:** `XState::handle` loops `XPending` and fetches each `XEvent` via `XNextEvent`. It first calls `grabber->handle(ev)` which delegates to `Children::handle` for window hierarchy/property events (`grabber.cc`). If not consumed, `XState::handle_event` processes it.
- **Core X events:** In `XState::handle_event`, `EnterNotify` updates `current_app_window` via `get_app_window`, and `ButtonPress` (core) calls `Handler::press_master`. This is used by `SelectHandler` for window selection and `ScrollHandler`’s core-button handling (`handler.cc`).
- **XI2 events:** `XState::handle_event` dispatches `GenericEvent` with `XGetEventData` and calls `XState::handle_xi2_event` (`handler.cc`). 
  - **ButtonPress:** sets `current_app_window`, sets `current_dev` from `grabber->get_xi_dev`, updates `modifiers` from XI2 state, pushes button into `xinput_pressed`, computes `in_proximity`, then calls `Handler::press` with a created `Triple` (`handler.cc`).
  - **Motion:** calls `Handler::motion` with root coordinates.
  - **RawMotion:** computes proximity and calls `handle_raw_motion`, which scales absolute device values and calls `Handler::raw_motion` (`handler.cc`).
  - **HierarchyChanged:** calls `Grabber::hierarchy_changed` to re-enumerate devices (`grabber.cc`).
- **Handler stack transitions:** `Handler::replace_child` swaps the active handler, updates grabs via `grabber->grab(new_handler->grab_mode())`, calls `child->init()`, and drains deferred queued actions (`handler.cc`).
- **Gesture flow:** `IdleHandler::press` (triggered by XI2 ButtonPress) creates `StrokeHandler`. `StrokeHandler::motion` accumulates points and draws trace; `StrokeHandler::release` creates a `Stroke`, runs `ActionListDiff::handle`, then converts actions into handler states (e.g., `ButtonHandler`, `IgnoreHandler`, `ScrollHandler`) or executes command actions.
- **Event suppression/replay:** Grabs are managed by `Grabber::grab_xi` and `Grabber::grab_xi_devs`. When actions should pass clicks through, handlers use `XTestFakeButtonEvent`/`XTestFakeMotionEvent` to replay into the X server (`handler.cc`).

**3. State Management Analysis**
- **Grabber state machine:** `Grabber::State` is `NONE`, `BUTTON`, `SELECT`, `RAW` (`grabber.h`). `Grabber::set` uses `active`, `disabled`, `suspended`, and current handler state to choose between `XIGrabButton`, `XIGrabDevice`, or `XGrabPointer` (SELECT) (`grabber.cc`).
  - Invariant assumed: `current` reflects the active `Handler::grab_mode()` (`Handler::replace_child`).
- **Handler stack state:** `Handler` owns `child`/`parent` pointers; stack top receives events. `replace_child` deletes the previous child and installs a new one (`handler.cc`). This is a single-threaded state machine but relies on correct ordering of handler teardown vs. pending timeouts.
- **Gesture recognition state:** `StrokeHandler` tracks `is_gesture`, `drawing`, `cur` (PreStroke), `orig/last` positions, and timeouts (`init_timeout`, `final_timeout`). It sets up timeout connections via `Glib::signal_timeout` and may abort the stroke on timeout (`StrokeHandler::timeout`) (`handler.cc`).
- **Global input state:** `XState` tracks `current_dev`, `xinput_pressed` (set of pressed XI buttons), `modifiers`, and `in_proximity` (`handler.cc`, `handler.h`). Many handlers gate behavior on `xinput_pressed.size()` and `in_proximity`.
- **Per-app activation state:** `Grabber::update` uses `current_app_window` → `current_class` and `prefs` (exceptions/whitelist) to enable/disable grabs; when `recording` is true, these app checks are bypassed (`grabber.cc`, `actions.cc`).

**4. Identified Hotspots**
- **`handler.cc` `XState::handle_xi2_event` (XI_RawMotion):** accesses `current_dev->proximity_axis` before checking `current_dev` (`handler.cc`). If `XI_RawMotion` arrives when `current_dev` is null (e.g., raw motion without a prior button press), this dereference can crash. The downstream `handle_raw_motion` has a guard, but the `in_proximity` assignment does not.
- **`handler.cc` `StrokeHandler` constructor:** reads `xstate->current_dev->name` to look up per-device timeout (`handler.cc`). This assumes `current_dev` is set by the preceding XI2 press path; if `StrokeHandler` is ever created outside that path, it can dereference null.
- **`grabber.cc` `Grabber::set` / `grab_xi_devs`:** transitions between XI grab states based on current handler state and `disabled`/`active`. The combination of `grab_xi` and `grab_xi_devs` is subtle: in `BUTTON` state, it uses `XIGrabButton` but does not `XIGrabDevice`, relying on XI2 passive grabs to deliver motion/button events. Any mismatch between handler state and `Grabber::current` can leave the system ungrabbed or overly grabbed.
- **Event replay logic:** `ButtonHandler`, `IgnoreHandler`, and `ScrollHandler` use `XTestFakeButtonEvent`/`XTestFakeMotionEvent` to synthesize input (`handler.cc`). This assumes synthetic events should be delivered to the master device and not re-captured by Easystroke. The only explicit control is `XTestGrabControl(dpy, True)` in `main.cc` (no further checks).
- **Select-window flow:** `XState::select_window` calls `gtk_main()` while a `SelectHandler` is active, uses `XState::ping()` and `WaitForPongHandler` to exit (`handler.cc`). This depends on ClientMessage ordering and GTK/X11 main loop interleaving; the timeout is 100ms (`WaitForPongHandler`), so any delayed ping/pong could trigger `bail_out`.
- **Fork-specific/experimental paths:** 
  - `Grabber::grab_xi` has an alternate path (`experimental`) that grabs extra buttons on disabled devices, with a comment “modified behaviour” (`grabber.cc`). This changes the global grab matrix.
  - `XState::handle_xi2_event` modifies `event->detail` on release for excluded devices by adding 100 (fake default button), and `StrokeHandler::release` reverses this (`handler.cc`). This introduces a synthetic button ID range (100+), which is a fork-specific convention not otherwise encoded in `ButtonInfo`.
  - `handler.cc` contains a large block around `AbstractScrollHandler` with comments like “Missing member variables” and “Ensure this is included at the top”, suggesting manual patching. This increases fragility and makes the control flow harder to reason about.
  - `actions.cc` contains a stub-style `negate` function and an inline lambda using it for selection logic (`actions.cc`), which looks like a forked modification of GTK selection behavior.

**5. Complexity Assessment**
- **Mixed responsibilities in `handler.cc`:** Input dispatch, gesture recognition, action replay, scroll synthesis, and UI selection logic (SelectHandler) are all in one file. This blurs the line between XI2 event handling and high-level action logic, making it harder to isolate event flow and state invariants.
- **Grabber does both device and window management:** `Grabber` handles XI2 device enumeration/grabs and also tracks window hierarchy/WM state (`Children`, `get_app_window`, minimized list) in `grabber.cc`. These are orthogonal responsibilities and increase coupling between input interception and window management.
- **Global state spread across modules:** Global `xstate`, `grabber`, `win`, `current_app_window`, `trace`, `recording`, and `experimental` are shared across modules (`main.cc`, `handler.cc`, `grabber.cc`, `actions.cc`). Control flow often depends on these globals without explicit ownership or lifetime guarantees.
- **Event deferral logic is implicit:** `XState::queue` + `Handler::replace_child` defers actions while a handler child exists. This is an important but implicit ordering constraint that can hide bugs when new handlers or UI callbacks are added.

**6. Crash-Risk Summary (Most Likely First)**
1. **Null dereference in XI_RawMotion path:** `XState::handle_xi2_event` reads `current_dev->proximity_axis` without a null check for RawMotion (`handler.cc`). If RawMotion is delivered when `current_dev` is unset, this is a direct crash.
2. **Device pointer lifetime and assumptions:** `StrokeHandler` constructor dereferences `xstate->current_dev->name` (`handler.cc`), assuming current_dev is always valid. If any event path constructs `StrokeHandler` without a valid XI2 press (or after device removal), this can crash.
3. **Handler stack + timeouts:** `StrokeHandler` uses multiple `Glib::signal_timeout` connections and replaces itself during callbacks (`handler.cc`). Although connections are stored in `shared_ptr`, handler replacement deletes the current handler. Any unexpected reentrancy could cause use-after-free if a callback fires after deletion.
4. **Experimental button-ID remapping:** Modifying `event->detail` in `XState::handle_xi2_event` (`handler.cc`) and undoing in `StrokeHandler::release` assumes all downstream logic tolerates “fake” button IDs. If any handler (or action mapping) assumes real XI button IDs, behavior may be undefined or incorrect (and could crash if used as array index elsewhere).
5. **X11 grab failure path:** `Grabber::set` calls `XGrabPointer` in SELECT state and throws `GrabFailedException` on failure (`grabber.cc`). The exception is caught in `XState::handle` and calls `bail_out`. If the exception occurs while the handler stack expects a different state, input could become stuck or the UI could misbehave.

**7. Open Questions (Need Runtime Validation)**
- **RawMotion ordering:** Does the XI2 server deliver `XI_RawMotion` to Easystroke when no button is pressed (and `current_dev` is null)? This determines whether the crash in `XState::handle_xi2_event` is reachable.
- **Synthetic event re-capture:** Are `XTestFake*` events seen by Easystroke while grabs are active? `XTestGrabControl(dpy, True)` is set, but the code assumes synthetic events will not loop back into the handler stack.
- **Multi-device behavior:** `xinput_pressed` gates behavior to a single `current_dev`. If two devices send overlapping presses, the code ignores events for other devices (`XState::handle_xi2_event`). Is that acceptable for the fork’s “global interception” goal?
- **Experimental path correctness:** The “fake default button” scheme (`event->detail += 100`) assumes no other component interprets button IDs directly. This should be validated against action mapping, prefs serialization (`ButtonInfo`), and UI display logic.
- **Select-window flow robustness:** `XState::select_window` enters `gtk_main()` and relies on a ping/pong ClientMessage to quit. If window manager or X server delays messages, the 100ms timeout may prematurely abort selection.
